在给你"清单"之前，先问你一个问题，让你自己先停下来想几秒：

> **你觉得 2026 年的前端开发者和 2024 年比，工作内容到底变在哪了？是写得更快了，还是写的"东西"本身变了？**

如果你只回答"更快了"，那需要补的就是工具熟练度；如果你意识到"东西本身变了"——产品里多了 chat、多了流式生成、多了 Agent，CR 流程换了、需求形态换了——那你要学的就远不止 Cursor 怎么用。

下面我给你一张三层能力地图，你看完可以对号入座。

---

## 第一层：把 AI 当工具（2026 年的"会用电脑"）

这一层是 **入场券** ，没有就直接被淘汰，有也算不上差异化。

**(1) Prompt / 上下文工程的基本盘**

不是背 prompt 模板，而是理解三件事：

* 模型为什么会幻觉 → 它在做下一个 token 预测，不是查数据库
* 上下文窗口是什么 → 决定它能"看见"多少
* 为什么同一个问题答得一会好一会坏 → 采样、temperature、上下文污染

**(2) 主流编码工具的实际操作**

不是都得精通，但你应该都摸过：Cursor、Claude Code、Trae（字节）、Copilot Agent 模式。重点不是工具本身，而是它们背后的 **交互范式** ——IDE 内嵌 vs CLI vs Web Agent，三种你都该用过一次。

**(3) 关键反向能力：判断 AI 什么时候是错的**

这条最容易被忽略，但 2026 年它就是 L3/L5 的分水岭。AI 给你写了一个看起来能跑的 useEffect，你能不能 30 秒内看出它把依赖项写错了？给你生成了一段类型，你能不能看出它用了 `any` 在偷懒？

> 检验自己的方法：把 AI 写的 PR 关掉提示直接审，看你能不能挑出问题。挑不出问题，说明你的水平已经被它兜住了——这不是好事。

---

## 第二层：把 AI 当工程基础设施（差异化开始的地方）

这一层是 2026 年大厂招中高级前端的硬指标。

**(1) Spec / 上下文工程（不是 Prompt 工程）**

学会写 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules`。它们的本质是把你团队的隐性知识（组件库怎么用、目录怎么放、命名规范、状态管理选型）显性化成 AI 能消费的文档。

试着回答这个问题来检验自己：

> *如果让一个完全不懂你们项目的资深前端，仅凭一份 Markdown 就写出符合规范的代码，这份 Markdown 该写什么？*
> 写得出来，你就掌握了上下文工程。写不出来，说明你团队的规范本身就是模糊的。

**(2) 类型驱动的 AI 协作**

TypeScript 在 AI 时代的角色变了。它不只是给 IDE 看的， **是给 LLM 看的提示词的一部分** 。类型写得越精，AI 生成越准；类型写得越松（满屏 `any`），AI 越容易瞎编。

要补的具体技能：泛型、条件类型、类型推导、`satisfies`、模板字面量类型、Zod/Valibot 这种 runtime + 类型一体化的库。

**(3) MCP 与 Skills 生态**

MCP（Model Context Protocol）让 AI 能调用你内部的 API、数据库、组件库文档、监控系统。Skills 是把"开发一个表单页"这种工作流封装成可复用的能力。

要会做的事：

* 写一个简单的 MCP server，把你团队的组件库文档暴露给 AI
* 配置 Claude Code 或 Cursor 接入这个 MCP
* 把高频任务（建页面、对接接口、加埋点）封装成 Skill

**(4) AI 进 CI/CD**

把 Claude Code/Gemini CLI 接进流水线，做的事可以是：自动写 PR 描述、自动审代码、自动补单测、自动生成 Release Notes。这部分很多团队还没做，做好了能直接出业绩。

---

## 第三层：会做 AI 原生产品（高价值前沿）

这一层决定你是"会用 AI 的前端"还是"AI 时代的前端"。差距是数量级的。

**(1) LLM API 与流式 UI**

要熟悉的 API 概念：

* Streaming（SSE、流式文本/JSON）
* Function calling / Tool use
* Structured output（JSON Schema、Zod schema）
* 多模态输入（图片、PDF）

要会的库： **Vercel AI SDK** （前端事实标准）、 **LangChain.js** （重一点的编排）、原生 `fetch` 对接 Anthropic/OpenAI API。

**(2) AI 原生的 UX 模式**

Chat 只是入门，真正变化大的是：

* **Generative UI** ：模型不是返回文字，是返回 UI 组件描述，前端动态渲染（v0、Vercel AI SDK 的 `streamUI` 都在做）
* **流式表单/流式表格** ：边算边渲染，不再 loading 转圈
* **可中断/可编辑的 Agent UI** ：用户能在 Agent 跑到一半叫停、改方向（Claude Code、Cursor 的 plan 模式都是这种）

要思考的设计问题：当输出是不确定的，UI 怎么处理？错误态怎么设计？怎么让用户信任不可预测的结果？

**(3) RAG 的前端视角**

你不一定要懂向量数据库的内部，但要懂：embedding 是什么、为什么要 chunk、检索结果怎么传给模型、怎么做引用展示（citation UI）。如果团队让你做"基于公司文档的智能问答"，你要能搭起来。

**(4) Eval 与可观测性**

AI 功能上线后怎么知道它好不好用？这是 2026 年的新前端工程问题。学会：

* 写 eval（用测试集自动评测模型质量）
* LangSmith、Langfuse 这类追踪工具
* 用户反馈回流（thumbs up/down → 数据集 → 调 prompt）

**(5) 安全与成本**

* Prompt injection 防御（用户输入混进 prompt 怎么办）
* 敏感数据脱敏（不能把用户隐私直接喂给云端模型）
* Token 成本控制（缓存、模型分级、prompt 压缩）
* 模型降级方案（云端不可用时降到本地小模型）

---

## 元能力（这层比工具更重要）

抛开具体技术，最该练的是这三种思维：

1. **需求拆解能力** ——能把"做个智能客服"这种模糊需求拆成"流式对话 UI + RAG 检索 + 工具调用 + 反馈收集"这种可执行清单
2. **判断力** ——AI 给你十种方案，你要能秒选最对的那一种，并说出为什么
3. **写作能力** ——给 AI 写 spec 的本质就是写作。Stripe 前 CTO 那句话适用每个开发者：花时间把想法写清楚，回报是巨大的

---

## 怎么排优先级

我的建议是这样：

| 你的当前状态                    | 该先补哪一层                                            |
| ------------------------------- | ------------------------------------------------------- |
| 还没系统用过 Cursor/Claude Code | 先把第一层吃透，1–2 个月                               |
| 工具用得熟，但项目里全靠手感    | 攻第二层的 Spec 工程 + MCP，3 个月                      |
| 第二层都顺，想往上走            | 第三层挑一个真实项目实战（哪怕是个 side project），半年 |

---

最后留你一个反思题，你可以认真回答自己（不一定回我）：

> **你最近一次写的代码里，有多少行是 AI 写的？这些代码你能完整解释每一行吗？如果不能，是因为 AI 太聪明，还是你太懒了？**

这个问题没有唯一答案，但它能帮你判断自己是在"借助 AI 成长"还是"被 AI 架空"。
