> 两列卡片、间距均匀、内容高度不定，还要底边齐平、尽量铺满整屏——这个听起来只是「摆几个盒子」的需求，其实把 Flexbox 与 Grid 的高度分配机制考了个遍。本文拆解三种业界常见的实现，只保留最核心的 CSS，并解释每一行为什么要这么写。

---

## 一个「看起来简单」的需求

先把需求说清楚。一个运维工作台由若干卡片组成，分两列，卡片之间有水平和垂直间距。要求是：

- **最底部的卡片，底边要高度对齐**；
- 最理想的情况下，底部卡片正好**铺满整个页面高度**；
- 但每张卡片的高度**不固定**，一般由内容决定，且应该有一个**最大高度**。

难点就藏在最后一条和现实的叠加里：屏幕高度因设备而异，卡片内容因时刻而异。同一套样式，在 1080p 显示器上内容不多时，可能下方一大片留白；在笔记本上告警爆发时，又可能把布局撑得参差不齐。

![自然堆叠导致底部参差，与「底部对齐、正好铺满」的目标对比](fig-01-goal.svg)

左边是什么都不做时的样子：两列各自堆叠，底边参差，下方还留白。右边是我们要的效果：每列末尾放一张**能伸缩的卡片**，把多余的高度吃掉，于是底边齐平、正好铺满。下面三种方案，本质都是在回答同一个问题——**剩余的高度交给谁**。

---

## 方案一：弹性卡片双列

最轻量的做法，十几行 CSS 就能满足全部要求，适合信息架构相对固定、不需要用户自定义拖拽的工作台首页。

思路：普通卡片保持「内容决定高度 + 设最大高度」，而**每一列指定一张弹性卡片**（通常挑表格、日志、图表这类天生可伸缩的内容），用 `flex: 1` 把该列剩余的高度全部吸收掉。

### 核心 CSS

```css
.dashboard {
  display: flex;
  gap: 16px;
  min-height: 100dvh;      /* 关键①：内容少→正好铺满；内容多→整页滚动 */
}

.column {
  flex: 1;
  min-width: 0;            /* 关键②：防止内容把列宽撑破 */
  display: flex;
  flex-direction: column;
  gap: 16px;
}

.card {                    /* 普通卡片：内容驱动高度 + 上限 */
  flex: none;
  max-height: 340px;
  overflow: auto;          /* 超过上限，卡片内部滚动 */
}

.card--elastic {           /* 每列一张：吸收剩余高度 */
  flex: 1;
  min-height: 0;           /* 关键③：内容过多时收缩滚动，守住等高与对齐 */
  overflow: auto;
}
```

### 为什么这么写

**为什么底边一定对齐？** Flex 容器的 `align-items` 默认值是 `stretch`，所以两列的高度永远被拉到一致，都等于 `max(视口高度, 较高一列的自然高度)`。既然两列等高、又都从容器顶部开始，各自的底边自然落在同一条线上。这一条是「免费」的，不需要任何额外代码——只要用 flex 布局两列，等高就是默认行为。

**为什么 `min-height: 100dvh` 能同时应付两种场景？** 这是整个方案的点睛之笔。

- 内容**少**时，两列的自然高度不足一屏，`min-height` 生效把容器顶到视口高度，多出来的空间由 `flex: 1` 的弹性卡撑开——于是正好铺满，底边贴住屏幕下缘。
- 内容**多**时，某一列自然高度已经超过一屏，容器随之变高、页面整体滚动。但因为 `align-items: stretch` 仍然让两列等高，较矮那一列的弹性卡会被拉伸到和较高列一样长——**底边依旧对齐**。

用的是 `100dvh` 而不是 `100vh`，是为了避开移动端浏览器地址栏收起/展开时 `vh` 不更新、导致内容溢出的老问题。

**为什么弹性卡要写 `min-height: 0`？** 这是最容易被忽略、也最容易翻车的一行。多数时候弹性卡靠 `flex: 1` 往大了长，把富余撑满；但当它自己内容很多、又恰好落在较矮那一列时，若不加约束，它会一路顶破所在列的高度，让两列不再等高、底边错位。`min-height` 默认是 `auto`（含义是「不小于内容高度」），恰恰会纵容这种撑破。显式写成 `min-height: 0`，弹性卡才肯在空间不够时**收缩、并把超出的内容交给内部滚动**，从而守住等高与对齐。至于普通卡片的溢出，则由它们自己的 `max-height + overflow: auto` 消化。

![内容少时弹性卡撑满视口；内容多时整页滚动，但两列等高、底边仍对齐](fig-02-elastic-columns.svg)

这套方案唯一需要做的产品决策是：**每列挑哪张卡片当弹性卡**。它左右独立堆叠，像两条各自流动的瀑布，因此左右卡片的水平分割线并不对齐。如果你的设计要求「同一行的左右卡片顶边也对齐」，就该看方案二。

## 方案二：单 Grid 行对齐

方案一的两列是**各自独立**的；方案二把两列塞进**同一个 Grid**，让行由两列共享，于是同一行的左右卡片水平线对齐，视觉更整齐。很多云控制台的首页用的是这种。

### 核心 CSS

```css
.dashboard {
  display: grid;
  grid-template-columns: repeat(2, minmax(0, 1fr));  /* 两列等宽，minmax(0,…) 防撑破 */
  grid-template-rows: auto auto minmax(220px, 1fr);  /* 关键：前两行内容驱动，末行吸收剩余 */
  gap: 16px;
  min-height: 100dvh;
}

.card {
  min-height: 0;           /* Grid 子项内部滚动，同样靠这一行 */
  max-height: 340px;
  overflow: auto;
}

.card--fill {              /* 落在末行的卡片：允许被 1fr 拉满 */
  max-height: none;
}

.card--span2 {             /* 需要跨两列的通栏卡片 */
  grid-column: 1 / -1;
}
```

### 为什么这么写

**行高从哪来？** 关键在 `grid-template-rows: auto auto minmax(220px, 1fr)`。前两行是 `auto`，高度由该行里较高的那张卡决定（并受各自 `max-height` 约束）；最后一行是 `1fr`，把容器减去前面所有行和间距后**剩下的高度全部拿走**。这就实现了「前面按内容排布、末行兜底铺满」，末行卡片的底边自然贴住容器下缘。`minmax(220px, 1fr)` 里的 `220px` 是个下限——窗口特别矮、`1fr` 算出来不足 220px 时，用 220px 兜底，此时页面出现整体滚动而不是把末行压没。

**和方案一到底差在哪？** 差在「行」是不是共享的。Grid 里同一行的所有单元格默认也是 `stretch`，会被拉到等高。好处是左右卡片的顶边、底边都对齐，横平竖直；代价是**同一行里内容少的那张卡，会被拉伸出一片留白**。如果不想被拉伸，可以对那张卡单独写 `align-self: start`，但它的底边就不再和邻居平齐了——这是个取舍，不是对错。

![两列共享 Grid：同一行左右对齐；末行 1fr 吸收剩余高度，代价是同行矮卡被拉伸](fig-03-grid-rows.svg)

**列宽为什么写 `minmax(0, 1fr)` 而不是 `1fr`？** 因为 `1fr` 的最小值同样默认是 `auto`，一段不换行的长文本或一张宽表格会把列顶破、撑出横向滚动条。把最小值显式设成 `0`，列宽才会老老实实按比例分配，内容超了就在卡内滚动。

## 方案三：严格铺满大屏

前两种在「内容特别多」时都允许整页滚动。但值班大屏、NOC 电视墙这类场景往往有条硬性要求：**页面绝不能出现滚动条**，任何屏幕、任何内容量，都要在一屏内消化完。

实现上和方案一只差一个字：把 `min-height: 100dvh` 换成 `height: 100dvh`，再给 `<body>` 加 `overflow: hidden` 锁死页面滚动。但这一换，意味着卡片总高被死死钉在一屏内，于是卡片必须**可压缩**——这就引出了三类卡片的分工。

### 核心 CSS

```css
html, body {
  height: 100%;
  margin: 0;
  overflow: hidden;         /* 页面级滚动被禁用 */
}

.dashboard {
  height: 100dvh;
  display: flex;
  gap: 12px;
}

.col {
  flex: 1;
  min-height: 0;            /* 允许列小于内容总高，是压缩链条的起点 */
  display: flex;
  flex-direction: column;
  gap: 12px;
}

.card.fixed  { flex: none; }                        /* 固定：不参与压缩 */
.card.shrink { flex: 0 1 auto; min-height: 128px; } /* 可压缩：空间不够先压它，到底线为止 */
.card.fill   { flex: 1 1 0;   min-height: 128px; }  /* 弹性：吸收 / 让出剩余高度 */

.card .body  { min-height: 0; overflow: auto; }     /* 压出来的内容，去处是卡内滚动 */
```

### 为什么这三类卡片能各司其职

先把三个 `flex` 简写展开，一切就清楚了：

```css
flex: none;     /* = flex: 0 0 auto  → grow:0 shrink:0 basis:auto */
flex: 0 1 auto; /* → grow:0 shrink:1 basis:auto */
flex: 1 1 0;    /* → grow:1 shrink:1 basis:0    */
```

因为列高被 `height: 100dvh` 定死，Flexbox 必须让三张卡的高度之和**恰好**等于列高。空间多了按 `grow` 分盈余，空间少了按 `shrink` 摊亏空——三类卡片只是把这几个旋钮拧到了不同位置。

- **`.fixed`（grow:0, shrink:0）**：两套分配机制它全退出了。空间再多不长、再少不缩，永远等于内容高度。所以 KPI 行这类东西「寸土不让」。

- **`.shrink`（grow:0, shrink:1, basis:auto）**：平时以内容高度呈现，空间不足时它是**唯一真正参与摊派亏空**的卡。这里 `min-height: 128px` 干了两件事，第二件很隐蔽：它既是「最少留 128px」的下限，更**覆盖了默认的 `min-height: auto`**——不改这条，`shrink: 1` 形同虚设，卡片根本压不动。压到 128px 后被冻结，多出的内容交给卡内滚动。

- **`.fill`（grow:1, shrink:1, basis:0）**：`basis: 0` 是最值得玩味的一笔。它让这张卡在计算时的「起始身高」为零——日志有 5 行还是 5000 行，对布局计算**毫无影响**。于是列高减去其它卡和间距后，剩多少盈余就全归它，它的最终高度是一个纯粹的「余数」。若写成 `flex: 1 1 auto`，日志一多，它的内容高就会进入基准总和，把布局拖进「按体积比例压缩」的模式，高度随日志条数漂移——流式日志每来一条，布局抖一下。`basis: 0` 把这种耦合彻底剪断，这才是「吸收或让出」的真正含义。

**窗口从高到矮，让出的顺序是固定的**，而且不是巧合：Flexbox 摊派压缩量时按 `flex-shrink × flex-basis` 的乘积加权。`.fill` 虽然 `shrink: 1`，但 `basis` 是 0，权重 = 1 × 0 = 0，所以它从不走「压缩」这条路变小，只因「盈余变少」而变小；`.shrink` 是唯一权重非零的卡，亏空全落在它头上。

![窗口从高到矮：先由 fill 交出富余，再压缩 shrink 到底线，fixed 始终不变](fig-04-squeeze-sequence.svg)

完整链条是这样的：窗口变矮 → `fill` 的余数先被吃掉 → `fill` 触到 128px 下限被钳住 → 亏空转嫁给 `shrink` → `shrink` 也压到 128px → 此时到达布局的「最小可用高度」（fixed 内容高 + 128 + 128 + 间距），再矮就只能溢出裁切了。换句话说，`min-height` 的取值实际上定义了这块大屏支持的最小分辨率。

顺带一提，展示型大屏还有另一派做法：固定按 1920×1080 出设计稿，所有元素绝对定位，外层容器用 `transform: scale(...)` 按视口等比缩放。文字会整体放大缩小，适合「只看不点」的电视墙，但不在本文的「内容驱动 + 弹性」范畴内。

## 三个必踩的坑

不管用哪种方案，下面三点缺一个，整套机制就哑火：

1. **`min-height: 0`**。Flex / Grid 子项默认 `min-height: auto`，会被内容撑破。凡是希望「卡片内部滚动」的地方，卡片及其滚动容器都要显式写 `min-height: 0`。这是这类布局出现频率最高的 bug。

2. **用 `100dvh`，别用 `100vh`**。移动端地址栏收起/展开时 `vh` 不变，会导致溢出或底部被裁。

3. **弹性卡选型**。`flex: 1` / `1fr` 的那张卡应挑内容天生可伸缩的类型（表格、日志、图表）。如果里面是图表，记得监听容器尺寸变化调用 `chart.resize()`（配合 `ResizeObserver`），否则容器变了、图表不跟着重绘。

另外两个体验细节顺手做掉：卡片头部用 `position: sticky` 固定、内容区滚动；给滚动容器加 `scrollbar-gutter: stable`，避免滚动条出现时布局左右抖动。

## 怎么选

| 场景 | 推荐方案 |
|---|---|
| 固定信息架构、只要底部对齐 + 尽量铺满 | 方案一（弹性卡片双列），最省事 |
| 需要同一行左右卡片水平线对齐 | 方案二（单 Grid 行对齐） |
| 值班大屏 / 电视墙，页面绝不滚动 | 方案三（严格铺满），或固定稿 + `transform: scale()` |
| 卡片种类会增减、要支持用户拖拽自定义 | 上 `react-grid-layout` / `vue-grid-layout` / `gridstack.js` 这类栅格系统 |

前三种方案的共同点，是把「剩余高度交给谁」这个问题显式地回答清楚——一旦想明白弹性卡片该放在哪、`min-height: 0` 该写在哪，剩下的就只是十几行 CSS 的事了。
